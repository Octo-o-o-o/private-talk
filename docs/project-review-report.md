# Private Talk 项目 Review 方案审查报告

## 1. 审查对象

- 文档：`docs/project-review-recommendations.md`
- 版本：V1
- 审查方式：对照当前代码、构建结果、测试结果进行一致性审查

## 2. 审查结论

审查结论：**通过，但需修订后作为最终执行方案。**

原因：

- 文档对项目的整体判断是正确的，已经明确指出“保留现有技术栈，先修 correctness，再做局部重构”，这和项目定位一致。
- 优先级排序基本正确，P0 / P1 / P2 的层次也合理。
- 但其中有几处提法还不够精确，直接照 V1 执行，可能会出现“方向对，但落地方式偏重或偏松”的问题，所以建议先修订为 V2 再作为正式方案。

## 3. 审查意见

### 3.1 关于排序字段的方案，需要进一步收紧

V1 中对排序问题给了两个可选方向：

- `created_at_ms / updated_at_ms`
- `message_seq`

这个表述对讨论阶段是够的，但对执行阶段还不够。

原因：

- 仅用毫秒时间戳，理论上仍可能冲突。
- 这个项目里已经有“按某条消息向后删除”“取第一条 user message”“按时间排序构造上下文”的逻辑，实际要求的是**稳定顺序**，不是“更细粒度的时间”。

修订建议：

- 把推荐方案收敛成“显式稳定顺序字段优先”。
- 也就是：
  - message 用稳定的顺序字段；
  - conversation 用稳定更新时间字段；
  - 所有依赖顺序的 SQL 都统一改掉。

### 3.2 关于上下文压缩的建议，需要补一句“原始消息保留，但不再参与重复压缩”

V1 建议引入 `conversation_summaries` 表，这个方向是对的。

但为了避免后续执行时有人误解成“压缩后把原始消息删掉”，建议补充一句设计约束：

- 原始消息继续保留在本地数据库中，作为完整历史；
- 摘要只服务于 prompt 构建；
- 已被摘要覆盖的冷区消息，不再重复进入下一轮压缩输入。

这样更符合这个项目“本地优先”和“保留完整历史”的定位。

### 3.3 关于 OpenClaw 的问题，需要把“当前工作树编译失败”和“链路未闭环”分成两层表述

这两件事相关，但不是一回事：

- “当前工作树编译失败”是当前状态问题；
- “无 CLI 回退 + Agent 缓存 + 连接串导入未闭环”是设计完成度问题。

如果混在一起，执行时容易出现一种误判：

- 只把编译修好，就以为 OpenClaw 方案完成了。

修订建议：

- 在正式方案中，把这两件事拆开：
  - 第一条：先恢复编译与最小可运行性；
  - 第二条：再补齐无 CLI 的完整产品链路。

### 3.4 关于“服务化整理”的建议，需要继续强调“只在复杂路径做，不做全项目推广”

V1 已经提醒“不要一口气搞成重型分层”，这点是对的。

但考虑到很多重构都死在“先定义大架构”上，我建议在最终版里再明确一点：

- 只允许对 `chat/context compression` 和 `openclaw` 两块做服务化整理；
- 其他 CRUD 型模块继续保持简单直接；
- 只有在重复 SQL 和分支逻辑已经明显影响可维护性时，才抽 service。

这样能防止方案被误执行成大规模抽象工程。

### 3.5 建议在最终方案中补上“验收标准”

V1 已经有执行顺序，但还缺一个更正式的收口条件。

建议在最终版每个阶段补一个最小验收标准，例如：

- P0 完成后：
  - Rust 可编译；
  - 发送 / 删除 / 重试 / 编辑消息链路稳定；
  - context compression 不再重复叠摘要；
  - OpenClaw 无 CLI 缓存回退可验证。
- P1 完成后：
  - 超大组件拆分完成；
  - 主包体积下降；
  - provider 选择不再被 reload 重置。

## 4. 审查决定

决定如下：

1. `docs/project-review-recommendations.md` 的总体方向成立。
2. 该文档可以作为正式方案的基础版本。
3. 在纳入执行前，必须先完成本报告中的修订项，形成 V2。

## 5. 审查后的建议动作

建议立即执行：

1. 将排序字段方案从“可选项”收敛成“首选方案”。
2. 在上下文压缩方案中明确“保留原始消息，但避免重复压缩”。
3. 将 OpenClaw 问题拆成“当前可编译性”与“完整产品链路”两条。
4. 在最终方案中补齐阶段性验收标准。

## 6. 最终回报

这份方案文档本身的判断是正确的，且已经足够作为项目下一阶段收敛的基础。  
需要做的不是推翻，而是把执行边界写得更严格一点，避免后续重构过度，或者只修表面问题而没有真正补齐链路。
