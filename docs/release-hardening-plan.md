# Private Talk 发布前加固方案（2026-03）

## 审查结论

当前分支已经具备正式发布的基础条件：

- `pnpm test` 通过
- `pnpm build` 通过
- `cargo test --manifest-path src-tauri/Cargo.toml` 通过
- 之前审查文档里的若干高优先级问题已经修复，例如：
  - user message ID 前后端一致
  - OpenClaw agent cache 的前端参数链路补齐
  - 路由级懒加载与代码高亮懒加载已经落地
  - 上下文摘要已迁移到 `conversation_summaries`

因此，这一轮不应该再做“推倒重来式”重构，而应该只处理仍然会影响发布质量的真实问题。

## 本轮值得实施的问题

### 1. 消息与会话排序仍然依赖秒级时间戳

当前后端多处逻辑仍然依赖 `created_at` / `updated_at` 的秒级文本排序，包括：

- 消息列表读取
- `delete_messages_from`
- 标题生成时“第一条 user message”的判定
- Usage 页首条消息预览
- 上下文压缩的消息顺序
- OpenClaw HTTP fallback 的历史构建
- 会话列表排序

这会带来两个问题：

- 同一秒内多条消息写入时，顺序语义不稳定
- “从某条消息开始删除”这种边界操作可能误删或漏删

这属于 correctness 和稳定性问题，必须处理。

### 2. PIN 的实现强度和产品语义不匹配

当前 PIN 仍然使用 unsalted SHA-256。即使这是本地功能，这也不符合一个面向开源发布项目的安全实现标准。

要点：

- 存储层应升级为带 salt 的 Argon2id
- 需要兼容已有 SHA-256 PIN，并在验证成功后自动升级
- UI 文案要明确：PIN 是本地隐私保护层，不应表述成完整设备级安全边界

这项改动风险低、收益高，值得实施。

### 3. Usage 页面默认发起外网请求，不符合 local-first 语义

当前 Usage 页面打开时会直接请求 OpenRouter 的模型定价，并在失败时把费用显示成 `$0.00`。

这会造成两个问题：

- 用户未主动要求联网，但页面已发生外网请求
- “没有价格数据”与“费用确实为 0”被混淆

正确做法应当是：

- 默认只展示本地 token 统计
- 将定价同步改成显式、按需触发
- 未同步定价时明确显示为“未同步/不可用”，而不是 `$0.00`

这项改动能同时改善产品语义和用户体验，值得实施。

### 4. 构建产物仍存在超大 chunk，缺少明确的 vendor chunk 策略

当前构建虽然已经有路由懒加载，但主包和 markdown/code 相关 chunk 仍然偏大，Vite 继续报警。

这不是阻断发布的问题，但它会影响：

- 首次加载解析成本
- 构建产物的可读性
- 外部开发者对工程质量的观感

适合做一轮低风险的 `manualChunks` 收敛。

## 本轮不建议做的事

### 1. 不做大规模组件拆分

`SettingsPage`、`Sidebar`、`ChatView` 仍然偏大，但它们当前不是 correctness 问题。正式发布前强行拆分这些大文件，收益没有大到足以覆盖回归风险。

这类重构值得做，但不应该和当前这轮发布加固绑在一起。

### 2. 不重做状态管理架构

`useAppStore` 仍偏重，但没有到必须在发布前重构的程度。继续用 Zustand 是合理的。

## 实施范围

本轮执行以下改动：

1. 为消息与会话引入稳定排序字段，并替换关键查询/删除边界逻辑
2. 将 PIN 升级为 Argon2id，并兼容旧哈希自动升级
3. 将 Usage 页改为默认离线优先、定价显式同步
4. 为 Vite 增加明确的 vendor chunk 切分策略
5. 为以上改动补充或更新测试

## 验收标准

- 同秒写入多条消息时，消息顺序仍稳定
- `delete_messages_from` 基于稳定顺序而不是秒级文本时间
- 会话列表排序不再依赖秒级 `updated_at`
- 旧 PIN 在验证成功后能自动升级为 Argon2id
- Usage 页面默认不触发外网定价请求
- 未同步定价时不再显示误导性的 `$0.00`
- `pnpm test`、`pnpm build`、`cargo test --manifest-path src-tauri/Cargo.toml` 再次通过
